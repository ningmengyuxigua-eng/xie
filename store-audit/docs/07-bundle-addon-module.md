# 組合銷售與加價購模組

## 目標

利用商品、流量、銷量、廣告與促銷資料，提高客單價。模組只產生候選和測試價；在成本資料通過驗證前，不把測試價標記為可獲利價格。

## 三層流程

1. 候選生成：使用商品 ID 去重，檢查庫存、近 30 天銷量／瀏覽量、進行中廣告與商品使用場景。
2. 定價試算：加價購測試 5%、10%、15% 折扣；兩件組合測試 3%、5%、8% 折扣。
3. 利潤閘門：正式採用前必須取得單位成本、平台費、增量運費及最低貢獻毛利。

## 候選規則

### 加價購

- 主商品應有近 30 天銷量、足夠瀏覽量或進行中廣告。
- 加購品必須有庫存，價格原則上為主商品最低價的 8% 至 55%。
- 商品名稱場景需相同或互補，例如廚房與清潔、浴室與收納。
- 已在進行中促銷的商品標記為衝突並先排除。

### 組合銷售

- 兩件商品需在相同或互補場景，價格不可相差過大，且都有庫存。
- 優先從有流量或銷量的商品帶動互補商品。
- 未取得訂單商品明細前，規則配對的信心上限為 `medium`；取得共同購買紀錄後才能升級為行為驗證候選。

## 定價公式

測試價：

- 加價購：`加購品現價 × (1 - 測試折扣率)`
- 組合：`商品 A 現價 + 商品 B 現價` 後再套用測試折扣率

正式最低價：

`商品成本合計 + 平台費用 + 增量運費 + 最低貢獻毛利`

若測試價低於正式最低價，候選必須被拒絕。平台費若按成交價計算，實作時需用費率反推含費售價，而不是簡單相加。

## 增量與效能

- 原始商品頁按日期留存，本模組只讀壓縮後商品目錄。
- 每次以商品 ID 更新，不重複累積相同商品。
- 對話只呈現最多 20 組候選；完整候選保存在本地 JSON。
- 每日增量只重新計算已變更商品及其配對；初版先全量計算建立基準。
- 定時任務及通知接口保留，現階段不啟用。

## 下一個資料閘門

需要一份以商品 ID 或規格 ID 對應的成本表，至少包含：`product_id`、`variation_id`（若有）、`unit_cost`、`effective_from`。同一商品反覆修改時，以 ID + 生效時間保存歷史，不覆蓋舊成本。

## 第一批實測發現

- 商品清單頁的價格欄位不完整，1,338 商品中只有 35 筆可直接辨識價格，因此清單頁不可作為正式定價來源。
- 依候選 ID 分批讀取 15 個商品詳情，15/15 成功取得目前規格售價。
- 15/15 都顯示參加「我的折扣活動 Any 2 enjoy 1% off」，建立新活動前必須檢查疊加／互斥規則。
- 商品層級的中位價只供篩選；正式價格鍵必須使用 `store_id + product_id + variation_id + effective_from`。

## 售價配置

2026-10-07 使用者提供的配置畫面顯示台灣站售價規則為：`採集售價 × 900% + TWD 20`，即 `採集售價 × 9 + 20`；「自動調整 SKU 五倍價」未啟用。該規則是售價生成依據，不視為成本欄位。任何組合或加價購調價仍需最低可售價保護。
