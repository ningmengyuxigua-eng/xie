# 效能與模型上下文契約

## 目標

資料可以每日增量成長，但抓取速度、資料庫查詢量和模型輸入量必須彼此分離。歷史資料增加時，模型單次接收的內容量保持固定。

## 每日同步流程

```text
建立 run_id
→ 讀取上次 checkpoint
→ 小批量取得資料
→ 每批保存原始證據
→ 寫入暫存表
→ 驗證與去重
→ 批次 UPSERT 正式資料
→ 更新摘要表
→ 提交 checkpoint
```

同步失敗時不回滾已確認完成的頁面，下一次從最後成功 checkpoint 繼續。

## 擷取限制

- 預設每批 20 筆，經實測後最多提高到 50 筆。
- 單次只擷取一種資料域。
- 廣告每日同步先讀取輕量列表，只對狀態為「進行中」的單品廣告和廣告群組讀取詳情。
- 暫停、已結束及已刪除廣告每週只做一次狀態核對；若重新啟用，再恢復每日詳情同步。
- 單品廣告只讀取一個商品關聯；廣告群組按商品頁分批讀取，並為群組保存獨立 checkpoint。
- 每頁完成後立即保存，不在記憶體累積全站資料。
- 每次執行設定最大頁數、最大時間及最大錯誤次數。
- 同一錯誤連續三次時停止該資料域，保存進度並報告。
- 正式擷取器禁止將完整 HTML、DOM 文字或全量 JSON 輸出到對話。
- 全量核對與日常增量分開執行。

## 原始資料格式與保留

- 新系統優先使用逐行 JSON（JSONL）或按頁小檔案，避免巨大 JSON 陣列。
- 路徑按 `store_id/data_domain/date/run_id` 分區。
- 每個原始檔記錄 checksum、來源 URL、擷取時間、解析器版本和批次 ID。
- 原始資料達到保留期限後壓縮封存；刪除策略另行確認。
- 正式資料庫不保存重複完整頁面文字。

## SQLite 寫入規則

- 啟用 WAL 模式。
- 每批資料在單一交易中完成。
- 使用 UPSERT 和唯一索引確保冪等。
- 寫入完成後才提交 checkpoint。
- 不逐筆開啟及關閉資料庫連線。
- 結構化金額、日期和數值在寫入前完成標準化。

## 必要索引

```text
products(store_id, product_id)
product_versions(store_id, product_id, valid_from)
product_observations(store_id, observed_at)
product_observations(store_id, product_id, observed_at)
ad_campaigns(store_id, ad_id)
ad_metric_observations(store_id, period_end)
ad_metric_observations(store_id, ad_id, period_start, period_end)
promotion_versions(store_id, promotion_type, promotion_id, valid_from)
order_items(store_id, ordered_at)
order_items(store_id, product_id, ordered_at)
sync_runs(run_id)
```

正式建立前需用實際查詢計畫驗證索引，而不是只根據表名建立大量索引。

## 查詢閘門

任何提供給模型的查詢必須經過統一閘門：

- 預設最多 20 行。
- 硬上限 100 行；超過只能輸出到本機報表。
- 預設文字結果不超過約 3,000 字元。
- 必須指定欄位，禁止 `SELECT *` 提供給模型。
- 必須指定 `store_id`。
- 時間序列必須指定日期範圍。
- 分頁使用穩定 Key，不使用大型 OFFSET。
- 預設查詢逾時 2 秒；報表查詢可使用獨立較長限制。
- 返回 `row_count`、`has_more`、查詢期間和資料時間，避免模型誤解結果完整性。

## 預計摘要表

- 每日商品表現摘要。
- 每日廣告表現摘要。
- 商品與廣告聯合摘要。
- 主商品與加購候選摘要。
- 促銷活動效果摘要。
- 異常商品及異常廣告清單。

模型先讀摘要。只有針對某個異常追查原因時，才按商品或廣告 ID 讀取少量明細。

## 模型上下文限制

- 禁止模型直接讀取整個 SQLite 資料庫、完整表、全量 JSON 或 HTML。
- 工具輸出上限是最後防線；資料必須在工具返回前完成篩選。
- 大型計算在本機 SQL 或分析程式完成。
- 大型結果保存為檔案，只把統計及檔案路徑交給模型。
- 每次對話只處理一個明確分析問題。
- 進度和決策寫入本機狀態，不依賴對話上下文保存。
- 發生輸出截斷、壓縮失敗或串流錯誤時，停止下一批並保留 checkpoint。

## 資料量預估

現有 1,338 個商品和 1,869 筆廣告資料。如果每天各產生一筆觀測，一年約增加 117 萬筆。只保存結構化數值並建立正確索引時，單機 SQLite 可以支援此量級；不能每天複製完整商品文字或整頁資料。

## 效能驗收標準

- 同一批資料重跑不增加重複行。
- 中斷後能從最後成功頁面繼續。
- 目前資料量的常用查詢目標低於 1 秒。
- 模擬一年資料後，常用索引查詢目標低於 2 秒。
- 日常同步記憶體用量不隨總歷史資料線性增加。
- 單次模型輸入不超過 20 行或約 3,000 字元。
- 單一資料域失敗不破壞其他資料域及既有資料。
- 每個分析結果可以追溯到 `run_id` 和原始證據。

## 擴充門檻

出現以下情況時再進行基準測試，評估將舊指標轉存 Parquet 並使用 DuckDB 分析：

- 資料庫成長到數 GB 至十數 GB。
- 常用索引查詢持續超過 2 秒。
- 需要多個程序或使用者同時寫入。
- 單日新增量達到數十萬至數百萬筆。
- 跨年分析需要頻繁掃描大量明細。

升級時保留 SQLite 管理目前狀態、同步批次及設定，不需要推翻 Key 和資料契約。
