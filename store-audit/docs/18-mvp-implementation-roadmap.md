# 拾味廚房雜貨鋪營運系統 MVP 實作路線

## 當前狀態

- 原型、資料Key、防卡架構、55天廣告回填、廣告決策、組合／加價購及報表中心藍圖已確認。
- 現有腳本仍包含探索期固定日期及個別入口，下一步需統一成正式每日流程。
- 定時任務、通知及店鋪自動修改仍保持關閉。

## 第一階段：凍結原型並建立正式MVP基線

1. 將設計基準標記為`1.0-mvp-baseline`。
2. 備份目前SQLite及核心配置檔，記錄SHA-256。
3. 建立版本化資料庫遷移目錄，不再直接修改初始化腳本後重建資料庫。
4. 套用已審核的報表中心資料表：`report_definition`、`report_run`、`report_artifact`。
5. 將店鋪展示名稱、時區、批次上限及報表上限集中到設定檔。

驗收：舊資料筆數不變、資料庫版本可查、遷移可重跑、所有報表仍顯示「拾味廚房雜貨鋪」。

## 第二階段：建立第一條正式每日流程

```text
檢查紫鳥連線
→ 讀取D-1進行中廣告
→ 回補D-3延遲歸因
→ 每20筆落盤與UPSERT
→ 資料品質檢查
→ 更新7日／30日摘要
→ 生成廣告日報
→ 寫入report_run及manifest
```

第一條流程只覆蓋廣告與資料品質，因為這兩個模塊資料最完整。失敗時保留checkpoint，不影響既有資料，也不繼續生成看似完整的報表。

驗收：同一天重跑不增加重複資料；D-1報表最多20個行動項；來源未變時不重算；CDP失敗可從最後頁續跑。

## 第三階段：接入正式報表中心

先生成兩張正式報表：

1. `ad_daily`：昨日指標、7日背景、擴量／維持／優化／停投候選及風險。
2. `data_quality_daily`：缺失日期、未配對、重複Key、來源差異、同步錯誤及報表完整性。

輸出固定包含`report.json`、`report.md`及`manifest.json`；需要人工篩選時才增加CSV。

驗收：報表可追溯到來源檔、規則版本和run_id；模型只讀摘要及最多20項，不讀原始CSV。

## 第四階段：建立人工審核與行動紀錄

- 為每條建議保存`pending_review`、`approved`、`rejected`、`executed`、`rolled_back`狀態。
- 保存廣告／商品ID、建議前值、批准值、執行值、執行時間和審核備註。
- 初期仍由人工在蝦皮操作；系統只記錄結果並於3天、7天後比較效果。

驗收：每次調整都能回答「為什麼改、誰批准、改了什麼、結果如何」。

## 第五階段：補齊盈利與客單價閉環

按以下順序接入缺少資料：

1. 商品及規格成本、生效日期。
2. 平台費、金流費及增量物流費。
3. 訂單商品明細及折扣分攤。
4. 庫存、安全庫存、重量和尺寸。

完成後才能正式啟用：損益平衡ROAS、組合／加價購最低價格、客單價提升及真實利潤報告。

## 第六階段：排程與通知

- 每日D-1廣告同步與報表。
- 每日取件超過4天提醒。
- D-3廣告回補。
- 每週商品流量、規則變更及全狀態核對。
- 每月廣告及商品月報。

排程只在前述流程連續穩定運行並經使用者確認後啟用；通知接口仍與分析流程分離。

## 立即執行項目

下一個開發批次只做第一至第三階段的最小閉環：

1. 建立資料庫備份與版本化遷移。
2. 正式套用報表中心三張資料表。
3. 把現有廣告D-1分析接入`report.json`契約。
4. 新增資料品質日報。
5. 用2026-10-07資料做一次完整重跑及冪等驗證。

此批次完成後再建立人工審核模塊，不同時接入成本、庫存或自動操作，以控制變更範圍。
