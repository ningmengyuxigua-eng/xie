## 為什麼不能一次讀完

以2026-10-07規模估算，廣告主表每日約126筆、7頁，30天約3,780筆、210頁；商品群組若全量展開，每日約31個有花費群組、93頁，30天可能接近2,790頁。資料庫可以保存這個量，但用瀏覽器一次讀完會增加CDP失效、頁面逾時及中斷後重來的風險。

### 路徑A：廣告匯出優先

1. 先測試蝦皮廣告報表能否一次選取30天並匯出每日明細。
2. 若匯出含日期、廣告ID及每日指標，原始檔只保存到本機，按20筆一批匯入SQLite。
3. 以`store_id + metric_date + ad_id`去重，重跑只更新。
4. 若匯出只有30天合計，保存為區間資料，不拆成虛構的每日數值。

這條路徑速度最快，瀏覽器只負責取得檔案，分析全部在本機完成。

### 路徑B：逐日頁面回填

匯出無法提供每日資料時，每次只跑一個日期：

```text
讀取7頁廣告主表
→ 每頁最多20筆立即落盤
→ SQLite UPSERT
→ 核對頁碼、筆數和checkpoint
→ 生成當日摘要
→ 結束程序並釋放頁面狀態
```

- 一次最多20頁；目前一個日期約7頁，因此每輪只處理1天最穩定。
- 每天是獨立job；任何一天失敗，不影響其他日期。
- 同一錯誤最多重試3次，仍失敗便保存checkpoint並停止該日。
- 每完成5個歷史日便執行一次資料庫核對，不連續跑完整30天。

## 商品層下鑽策略

不預設把30天所有廣告群組全部展開。先完成30天廣告主表，再用本機SQL選出：

- 30天花費最高但無轉換的群組。
- ROAS持續低於目標的群組。
- 有效轉換且可能擴量的群組。
- 單日異常且連續兩天以上重複出現的群組。

只有入選群組才按7天窗口讀商品層；每輪最多6個群組或20頁。若官方匯出能直接提供商品每日明細，則用匯出代替瀏覽器下鑽。

## 模型不會卡住的原因

- 原始JSON、HTML及匯出檔不進入對話，只保存在`store-audit/backfill`。
- 30天分析預設只傳30筆日彙總和最多20個異常項給模型。
- 半年分析只讀6筆月彙總，不重新讀每天與每個商品。
- 每日新增資料使用UPSERT及複合主鍵，不會因重跑而膨脹。
- 讀取速度由本次頁數控制，不會隨資料庫歷史總量線性變慢。

## 執行順序

1. 測試30天廣告匯出是否包含每日粒度。
2. 匯出可用：按匯出檔回填並核對每日總額。
3. 匯出不可用：從最早日期開始逐日跑廣告主表。
4. 完成30天主表後生成群組候選，不全量展開商品層。
5. 針對候選群組分5個七日窗口下鑽。
6. 生成30天日摘要、廣告總結及商品異常清單。

任何階段都優先讓每日D-1任務執行，歷史回填不得阻塞當日分析。
